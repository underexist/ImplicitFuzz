# 内核源码静态抽取层：技术路线与实现规范（v3）

> 整合截至 2026-07-08 的全部调研 + 两轮工程审阅。
> **v3 目标：从"合理的开发路线"升级为"能开工且能验收的实现规范"。**
> 抽取层职责边界：**从内核源码/LLVM IR 中抽取结构化的访问事实，不做身份判定之上的任何推断**。传递闭包、生产者-消费者配对、状态机建模留给证据库上层与后续阶段。
>
> **v3 相对 v2 的核心变化**：精确 patch 版本矩阵；优化等级改为对照矩阵（非 -O0 独断）；summary 升为 schema；`semantic_op`/`access_kind` 语义扩宽并厘清边界；`object_scope` 与 `instruction_id` 稳定性规则；entry_fact 补 io_uring 异步入口；TypeCopilot 降为离线对照参考；补入 BTF、门控分支切片、KCOV remote coverage、syzkaller 映射与外部静态工具定位；container_of 验证明确 ground truth 来源；golden test 量化验收。

## 第一部分：整体定位与架构

### 1.1 架构分层

```
┌──────────────────────────────────────────────────────┐
│  extraction/ (C++ 独立子项目，基于 SVF + LLVM)          │
│  输入：内核子系统 LLVM bitcode + 构建 manifest          │
│  输出：结构化事实 JSONL（带 provenance/confidence/稳定ID）│
│  内部：SVF 值流/指针分析 + 自研 access-path 符号化层     │
│        + primitive_summary（stub 语义库）               │
│        (离线对照参考) TypeCopilot 类型恢复               │
└──────────────────────┬───────────────────────────────┘
                        │ 进程边界，JSONL（唯一接口）
                        ▼
┌──────────────────────────────────────────────────────┐
│  src/implicitfuzz/ (Python 包)                         │
│  ingestion → SQLite；传递闭包/配对在 SQL 递归 CTE 计算   │
└──────────────────────────────────────────────────────┘
```

### 1.2 语言边界

值流/指针分析无成熟 Python 实现，SVF 是 C++/LLVM 库，重写等于推倒地基。抽取层必然是 C++ 子项目，与 Python 主体以 JSONL 为唯一接口，进程边界即可，不需 pybind11。

## 第二部分：技术栈与版本锁定（v3 精确到 patch）

| 项目 | 决定 | 备注 / 风险 |
|---|---|---|
| 值流/指针分析底座 | SVF 当前 HEAD | 官方支持嵌入自定义 C++ |
| LLVM 主版本 | **SVF `build.sh` pin 的 LLVM 21.1.0**（主干） | ⚠️ 见 2.1 patch 版本纪律 |
| LLVM 实验版本 | 21.1.8 等仅作实验矩阵单列 | 不作主干 |
| opaque pointer 恢复 | **TypeCopilot 仅作离线对照参考** | 官方锁 LLVM 16，非生产链，见 2.2 |
| 证据库 | SQLite + 递归 CTE | 传递闭包在查询层 |
| 主语言 | 抽取层 C++、主体 Python | JSONL 接口 |

### 2.1 ⚠️ LLVM patch 版本纪律（v3 新增，审阅必改项）

SVF 的 `build.sh` 当前 pin 的是 **LLVM 21.1.0**，而常规下载渠道可能给到 21.1.8。LLVM 的 C++ API/ABI、CMake package 路径、SVF 构建都可能受 patch 版本影响。**主干必须使用 SVF 脚本 pin 的 21.1.0**；若因故改用 21.1.8 或其他 patch，必须作为独立实验矩阵条目记录（含构建是否通过、API 是否需 patch），不得默认混用。LLVM 版本（精确到 patch）与 clang 编译内核所用版本必须一致，并写入构建 manifest。

### 2.2 opaque pointer 风险 + TypeCopilot 定位（v3 再降级为离线对照参考）

**风险**：较新 LLVM 默认 opaque pointer，指针统一为泛型 `ptr`、抹除 pointee 类型，冲击基于类型的分析。SVF 从 LLVM 16 起支持、且适配持续进行中，**其在 LLVM 21.1.0 下对 opaque pointer 的成熟度未实测**，是主干首要不确定性。

**TypeCopilot 定位（v3）**：`ZJU-SEC/TypeCopilot`（ISSTA'25，浙大，开源）解决 opaque pointer 类型丢失，内核准确率 94–98%。但其 CMake 明确 `find_package(LLVM 16 REQUIRED CONFIG)`、构建 `script/llvm.py build 16`，是绑定 LLVM 16 的 **research prototype**。
- **不预设它进入生产抽取链**。仅作**离线 differential reference / 对照参考**：在 LLVM 16 上跑 golden cases，为字段类型提供第三方参考，用于评估主干（LLVM 21 + SVF 原生）字段恢复的差距。真正的 ground truth 只有人工标注的 golden cases；TypeCopilot 输出与人工标注冲突时，以人工标注为准。
- 据评估结果再决定：主干是否需迁 TypeCopilot 到 LLVM 21、还是主干降到 LLVM 16/18、还是仅在低置信度场景选用。

## 第三部分：内核编译为 LLVM Bitcode

### 3.1 已排除：Crix / deadline

工具链绑定 LLVM 10 / 内核 4.13–5.3，目录黑名单、失败静默丢弃、复现失败 issue 无人跟进。不复用。

### 3.2 采用路线（二选一）

- **`wllvm`/`gllvm`**：拦截每编译单元产 `.bc`，`llvm-link` 合并（SVF 生态主流）。
- **内核原生 `LLVM=1`** + IR 捕获。

参考更新脚本：`ZHYfeng/Generate_Linux_Kernel_Bitcode`（v6.1/v6.6）、`umnsec/mlta` IRDumper。

### 3.3 优化等级：对照矩阵，非 -O0 独断（v3 更正过强表述）

> **v2 曾写"几乎所有相关工作都跑在 -O0"，不严谨，已更正**：arXiv 2404.00350（LLIF）明确在 Linux 5.14.11 上用默认 flags、`-O2 -g` 评估并成功恢复 container_of 字段。**-O0 有利于字段链保真，但不是唯一可行路线。**

**做法**：把优化等级做成 golden test 对照矩阵——`-O0` / `-Og` / `-O2 -g` 三档各跑一遍三个 golden case，用实测数据决定主干采用哪档。默认倾向：优先尝试 `-O2 -g`（贴近内核真实构建、别名分析精度/规模更好），仅当字段恢复率不达标再回退 `-Og`/`-O0`。优化档位写入 manifest。

### 3.3.1 BTF / DWARF 类型布局参考（补调研新增）

内核可通过 `pahole` 生成 BTF，BTF 记录类型、结构体/联合体成员名、成员类型与 bit offset，可用 `bpftool btf dump` 导出。它不替代 SVF 的值流/别名分析，但适合作为**字段布局参考源**：当 DWARF 信息缺失、GEP 符号化失败或 container_of 只恢复出数值偏移时，用 BTF 做结构体成员名与偏移的交叉校验。

落实到工程上：
- manifest 记录 `debug_info_kind`、`btf_available`、`pahole_version`、`vmlinux_btf_path`。
- `access_path_recovery` 增加 `btf` / `btf_partial`，并写入 `provenance[]`。
- BTF 只参与"字段布局解释"，不直接产生身份等价结论；若 BTF 与 DWARF/SVF 结果冲突，fact 仍保留，但置信度降档并记录冲突来源。

### 3.4 跨子系统依赖策略（open-world 起步）

io_uring 会拽入内存分配、vfs、task/workqueue、rcu、poll、security hooks、net、lib 等。**必须先定架构决策**：
- **open-world（建议起步）**：允许 unresolved external，对内核 primitive 用 `primitive_summary`（见 3.6）兜底。范围可控、启动快；跨边界值流在 stub 处按 summary 语义续接。
- **closure（按需扩展）**：对确实影响 access_fact 正确性的关键依赖（如自定义分配器所在 TU）再纳入 bitcode list，非一次性全闭包。

### 3.5 性能三档运行模式

SVF 全程序分析易爆内存，预定义：**TU 级**（golden tests/冒烟）、**子系统级**（io_uring 全 TU + primitive stub，主力）、**可达闭包级**（按需纳入跨子系统依赖）。

### 3.6 ⚠️ primitive_summary schema（v3 新增，审阅必改项）

stub/summary 不能停在概念层，定义为 `primitive_summary.yaml`。每条 summary 既要描述生命周期，也要描述副作用和副作用绑定到哪个参数，否则只能知道"发生了异步注册/容器链接"，不知道注册或链接的是哪个对象。每条至少含：

```yaml
- name_pattern: "queue_work*"            # 函数名/模式
  param_roles:                            # 各参数角色
    - {index: 0, role: workqueue_handle}
    - {index: 1, role: work_item}
  return_role: none
  lifecycle: none                         # allocate|free|free_async|retain|release|none
  is_async: true
  transfers_ownership: false
  retains_reference: true
  effects: [async_enqueue, callback_register]
  effect_bindings:
    - {effect: async_enqueue, target_param: 1, context_param: 0}
    - {effect: callback_register, callback_param: 1, context_param: 0}
  confidence: high                        # summary 本身可信度
```

`effects` 枚举先覆盖：
```
lock_acquire | lock_release
| container_link | container_unlink
| async_enqueue
| callback_register | callback_invoke
| copy_from_user | copy_to_user
```

io_uring 首轮 summary 清单至少覆盖：分配/释放族、`io_kiocb`/`io_ring_ctx` 相关 cache、RCU、`percpu_ref`/`refcount`、`llist`/`list`/`xarray`、`task_work`/workqueue/io-wq、mutex/spinlock、usercopy、completion/cancel/timeout。第七部分识别出的自定义分配/释放包装函数，其语义并入本库。

## 第五部分：JSONL 事实表（v3 实现规范级）

### 5.1 公共字段

| 字段 | 含义 |
|---|---|
| `schema_version` | fact schema 版本 |
| `kernel_version` | 内核版本 |
| `llvm_version` | 精确到 patch（如 21.1.0） |
| `opt_level` | 编译优化档（-O0/-Og/-O2 -g） |
| `bc_unit` | 来源 bitcode 单元/TU |
| `function` | 所在函数 |
| `instruction_id` | 稳定指令 ID，见 5.5 |
| `svf_node_id` | 对应 SVFIR 节点 |
| `source_location` | 宏/内联栈对象，见 5.5 |
| `primary_provenance` | 主导来源，用于置信度定档 |
| `provenance` | 来源数组，枚举含 `svf`/`dwarf`/`dwarf_partial`/`btf`/`btf_partial`/`typecopilot`/`container_of_heuristic`/`numeric_fallback`/`summary` |
| `confidence` | 置信度档位（第十部分） |

`source_location` 统一写成：
```json
{
  "spelling": "file:line",
  "expansion": "file:line",
  "inlined_at": ["file:line"]
}
```
其中 `spelling` 用于回到源码真实书写位置，`expansion` 用于跨优化档对齐，`inlined_at` 可为空。

### 5.2 `entry_fact`（v3 补 io_uring 异步入口）

`entry_kind` 枚举扩为：
```
syscall | file_op | callback | workqueue | ioctl | uring_cmd | task_work
| io_worker | sqpoll_thread | completion_path | timeout_callback | cancel_path
```
理由：io_uring 大量状态变化不从 syscall 栈同步发生，异步执行路径（worker、SQPOLL、完成/超时/取消回调）是隐式依赖高发区，必须建模为入口。字段：`entry_kind`、`entry_symbol`、`associated_syscall`（若可归属）。参考 SyzDescribe 命名与 knowledge.json。

### 5.3 `call_fact`

字段：`caller`、`callee`、`call_site`(instruction_id)、`is_indirect`、`resolution_method`(direct/mlta/pta)、`callee_candidates`（间接候选集）。
**上下文敏感（v3 预留，可后置）**：加 `context_depth`、`call_chain_hash`、`entry_context` 预留字段。⚠️ 第一版只填 `call_chain_hash` 作弱上下文标识即可——**全上下文敏感在内核规模会爆炸，SVF 默认也不开**，完整上下文敏感留后续按需开启，不要因这几个字段就一上来开全上下文分析。

### 5.4 `access_fact`（v3 扩宽 semantic_op 与 access_kind，并厘清边界）

**两个维度语义正交，不重叠（v3 厘清，审阅隐含冲突项）**：
- **`semantic_op`** 描述抽象语义操作：
  ```
  alloc | read | write | free | free_async | retain | release | escape
  ```
  其中 `alloc/free/free_async/retain/release` 属生命周期类，`read/write` 属数据访问类，`escape` 属逃逸类。`free_async` 专指 `kfree_rcu`/`call_rcu` 等延迟/回调释放，**不与同步 `free` 等价**，否则上层 alloc≺free 配对会把"注册延迟释放"误判为"已释放"。`retain`/`release` 对应 refcount 增减。
- **`access_kind`** 描述通过**什么指令形式**访问字段：
  ```
  direct_load | direct_store | memcpy | memset | atomic | usercopy | call_arg
  ```
  内核大量访问经 `memcpy`/`memset`/`copy_from_user`/`copy_to_user`/`atomic`/`READ_ONCE`/`WRITE_ONCE`/函数参数传递发生，只认 load/store 会漏。
  > **边界规则**：地址逃逸只记为 `semantic_op=escape`，不在 `access_kind` 里再设 `address_escape`，避免两字段语义重叠。`call_arg` 表示"字段值作为实参传出"，是否构成逃逸由 `semantic_op` 判定。

其他字段：`base_object`（见 5.6）、`object_scope`、`access_path_symbolic`（可空）、`numeric_kind`、`access_path_numeric`（按 `numeric_kind` 解释）、`field_type`、`access_path_recovery`(dwarf/btf/container_of_heuristic/numeric_only)。

`numeric_kind` 明确 numeric 的粒度：
```
gep_offsets | byte_range | whole_object | unknown
```
`unknown` 时 `access_path_numeric` 可为空，但 fact 仍产出。**失败不丢事实** 的含义是一定产出 fact、一定写 `numeric_kind`、confidence 降档，而不是强行伪造 GEP 偏移。

### 5.5 ⚠️ `instruction_id` 稳定性规则（v3 新增，审阅必改项）

**不能依赖 source location**——内核宏展开（`container_of`、`list_for_each_entry` 本身即宏）与优化会让多条 IR 指令共享同一 source loc，导致 ID 相撞、无法回溯。定义为：
```
instruction_id = module_hash : function : basic_block_ordinal : instruction_ordinal : ir_hash
```
`source_location` 仅作辅助展示，不参与 ID 生成。ID 生成规则写入 manifest，保证同一构建产物内可复现。

注意：`instruction_id` 只是 **build-local stable**，不承诺跨 `-O0/-Og/-O2 -g` 相同。跨优化档对齐使用：
```
cross_opt_key = source_location(expansion) + access_path_key + function + semantic_op
access_path_key = symbolic_path || numeric_repr || source_snippet_hash
```
即优先用符号化路径，其次用数值表示；两者都不可得时退到源码片段哈希，保证优化矩阵中低置信度 fact 也能参与对比。

### 5.6 ⚠️ `object_id` 稳定性规则（v3 新增，审阅必改项）

`alias_fact`/`access_fact` 的对象标识必须跨 TU、跨运行稳定。分类定义：
```
object_id =
    allocation_site_id(instruction_id)     # 堆对象：按分配点
  | global_symbol(name)                    # 全局对象：按符号名
  | param_object(function, arg_index)      # 入参对象：按函数+参数位
  | synthetic_stub_object(summary_name)    # summary 兜底产生的合成对象
```
同时写 `object_scope`：
```
allocation_site | global | formal_param | synthetic
```
生成规则写入 manifest。`formal_param` 与 `synthetic` 是**关系证据**，不能被证据库上层直接判为身份等价；必须沿 `call_fact` 的调用点 refine 到具体 allocation site/global 后，才可进入对象身份闭包。这个约束是避免 helper 函数把不同实际对象误合并的关键。

### 5.7 `alias_fact`（承 v2：存 points-to，非全量两两 alias）

存 `points_to_set`/`object_id`、`relation_evidence`（产生关系的指令/值流边）、`pta_kind`（Andersen/flow-sensitive）。**不存 O(n²) 全量两两 alias**（会爆炸且与"传递闭包在 SQL 层算"冲突）。传递闭包由证据库 SQL 递归 CTE 计算。

### 5.8 `branch_fact` / `gate_seed_fact`（补调研新增）

静态抽取层不仅要抽取对象访问，也要给后续隐式依赖推断提供"目标门控锚点"。新增两类 fact：

- `branch_fact`：记录条件分支、switch、错误路径判断、状态位判断。字段包含 `branch_instruction_id`、`condition_value`、`source_location`、`control_deps`、`related_loads`、`slice_range`。
- `gate_seed_fact`：把与 fuzzing 目标相关的分支标成门控种子。字段包含 `target_symbol`、`gate_kind`、`predicate_summary`、`related_objects`、`related_access_facts`、`confidence`。

实现上先做**branch-local backward slice**：从条件值向后沿 SVFG 追 value-flow，辅以 LLVM Dependence Graph/轻量控制依赖记录，不在第一版上全程序 SDG。这样可以先服务第四章的目标引导与依赖解释，不把抽取层做成第二个大型程序切片器。

### 5.9 排除的抽取层依赖

SyzGen/SyzGen++/INFUZE（闭源 macOS 二进制/符号执行路线，仅借"容器同一性"概念）；SyzSpec（KLEE 结构约束恢复，属后续阶段，本阶段不接）。

## 第六部分：Access-Path 符号化（本层最大自研）

### 6.1 地基

SVF `AccessPath` 只给数值化 `fldIdx`/`idxOperandPairs`/`gepPointeeType`，无字段名。需叠：`GEP 链 (operand,type) 序列 + DWARF/BTF 字段布局 + (离线对照参考) TypeCopilot 类型 → 符号化路径；失败保留 numeric_kind + numeric_repr`。

### 6.2 常规字段访问（golden case 1）

`ctx->buf_table` 类，验证 GEP+DWARF→字段名。⚠️ 优化+指针算术下 SVF 字段敏感性可能失效，允许 numeric fallback。

### 6.3 container_of 还原（golden case 2，v3 明确 ground truth）

> container_of 属"内存安全/类型混淆"文献线（与"依赖推断/别名分析"不同），有现成成果，**非自研空白**。

**重要性**：内核"面向对象"核心机制，`list_for_each_entry` 等高频宏依赖它。断裂 → 访问事实**系统性遗漏**。

**成果一 `vusec/uncontained`（USENIX Sec'23，开源）**：类型图建模 container_of，89 bug/149 补丁，`passes/DumpContainerOf`。⚠️ 深度绑定定制 LLVM+定制 Linux 子模块（fork 打补丁），锁 clang-12/内核 v5.15。
**成果二 LLIF（arXiv 2404.00350）**：纯 IR 算法，基指针递归字节偏移 `B_s` → 目标类型 `T` 的 bitcast 偏移 `B_c` → `B_s−B_c` 重构字段；`-O2 -g` 上验证有效；降级退回 debug metadata（只得容器类型）。

**v3 定位与验证方式（审阅必改项）**：
- LLIF 算法为**主参考，需自己实现**（非可 clone 即用组件）。
- **不与 uncontained 工程联跑**（它绑死自己的 LLVM/Linux 子模块，联跑成本高且无必要）。只复用其**测试思想与类型图输出概念**，把还原结果表达为三元组 `(container_type, member_offset, recovered_field_chain)`。
- ⚠️ **ground truth 来源（v3 补齐）**：三元组的"正确答案"由**人工标注** golden case 2 的那几个具体样例得到（样例数少，标得起），不依赖任何外部工具自动产出。这是 container_of 还原正确性的唯一独立验证锚点。

**受阻备选**：(a) 针对 container_of/list_head 高度模式化宏做专项启发式；(b) numeric offset + 低置信度先入库，符号化留执行验证兜底。

### 6.4 alloc wrapper 识别（golden case 3）

见第七部分，验证种子+传播能否识别一个 io_uring 自定义分配包装函数。

## 第七部分：Alloc/Free 识别（种子+传播，语义细分）

**背景**：内核走自定义包装函数，只认标准名单会系统漏报。

**Goshawk（SP'22）**：NLP+传播两阶段。**跳过 NLP**（移植/重训模型以周计），**复用"种子+传播"不动点**在 SVF 调用图/值流图重写（数天）。

**种子集与语义细分（v3 承 5.4 的 semantic_op 扩宽）**：
- 同步分配：`kmalloc, kzalloc, vmalloc, kmem_cache_alloc` → `semantic_op=alloc`
- 同步释放：`kfree, kmem_cache_free` → `semantic_op=free`
- **异步/延迟释放**：`kfree_rcu, call_rcu` → **`semantic_op=free_async`（不与 free 等价）**
- refcount：`*_get`/`*_put` 传播为 `retain`/`release`
**规则**：函数直接返回/透传已确认分配器返回值 → 标记为确认（free 侧同理），传播至不动点。识别结果并入 `primitive_summary`（3.6），保证 open-world 下值流不在包装函数断裂。

## 第九部分：与后续研究阶段的接口

### 9.1 面向隐式依赖图的最小输入

静态抽取层向后续阶段提供三类证据，不直接给出"最终依赖"：

1. 对象关系证据：`access_fact`、`alias_fact`、`call_fact`、`primitive_summary` 产生的 relation evidence。
2. 目标门控锚点：`branch_fact`、`gate_seed_fact`，定位状态判断、错误路径判断、异步完成路径判断等候选门控点。
3. 入口与异步路径：`entry_fact` 及 summary 的 `async_enqueue/callback_register/callback_invoke`，把 syscall 栈之外的 worker、task_work、completion、timeout、cancel 路径接回同一证据图。

这组输出能支撑第三章的依赖图构建，也能给第四章的目标调度提供候选"先满足哪些状态、再触发哪个入口"的证据。

### 9.2 与 syzkaller 描述的映射

抽取层不直接生成最终 syzkaller 规范，但要保留可映射字段：
- `semantic_op=alloc/retain/release/free` 与 resource 生命周期关联；
- `copy_from_user/copy_to_user`、`call_arg`、`field_type` 与 syscall 参数/结构字段候选关联；
- `gate_seed_fact` 中的 `predicate_summary`、`related_objects` 与后续"隐式门控参数"关联；
- `entry_fact` 中的 `syscall/file_op/ioctl/uring_cmd` 与 syzkaller syscall description 的入口关联。

第一版只要求能导出中间映射表，不要求直接生成可用 `.txt` 描述；等依赖图和执行验证稳定后，再让上层把这些证据合成为 syzkaller 资源、结构字段和约束。

### 9.3 SQLite 与 Datalog 边界

主线仍用 SQLite + 递归 CTE。原因是第一版规则数量有限，调试成本低，JSONL ingestion 也直接。若后续出现下列情况，再引入 Souffle/Datalog 做规模化规则引擎：递归规则超过 SQLite 可维护范围、跨 entry 的闭包查询性能不可接受、需要大量半格/固定点规则表达。Datalog 是扩展选项，不是第一版依赖。

### 9.4 动态验证接口

静态证据必须能被执行侧抽样验证。普通 syscall 路径可用 KCOV 覆盖；io_uring 的 worker、task_work、io-wq、后台线程路径可能脱离普通 KCOV 线程上下文，需要优先评估 KCOV remote coverage。若目标内核或场景无法稳定拿到 remote coverage，再把 kprobe/ftrace/eBPF 作为可选观测通道，用来确认异步入口、回调触发和门控分支是否被实际走到。

## 第十一部分：置信度模型

| 档位 | 来源 | primary_provenance |
|---|---|---|
| 高 | GEP+DWARF/BTF 直接符号化，且来源一致 | `dwarf` / `btf` |
| 中高 | container_of 字节偏移还原且与人工标注一致 | `container_of_heuristic` |
| 中 | TypeCopilot 对照参考恢复出的类型路径 | `typecopilot` |
| 中低 | 仅 debug metadata/BTF 得容器类型、无完整字段链 | `dwarf_partial` / `btf_partial` |
| 低 | 仅 numeric repr，或 `numeric_kind=unknown` | `numeric_fallback` |
| —（正交）| 来自 primitive_summary 的语义 | `summary`（confidence 取 summary 自带档） |

原则：**失败不丢事实**，任何档都产出 fact，写明 `numeric_kind`、`primary_provenance` 与 `provenance[]`；confidence 进入 JSONL，供上层查询、LLM 判读和执行验证按档加权。

## 第十二部分：实施顺序（三阶段）

### 阶段一：SVF21 最小链路（不接 TypeCopilot）
锁 LLVM 21.1.0 与一个已验证的 SVF commit，照抄 `svf-ex.cpp` 搭最小 driver；编 TU 级小 bitcode，输出最小 `call_fact`/`access_fact`（access path 可仅 numeric）；打通 bitcode→SVF→JSONL→SQLite。
⚠️ **头号观测目标**：SVF 在 LLVM 21.1.0 下对 opaque pointer 的原生处理成熟度（2.2）。**若阶段一即撞 opaque pointer 致字段信息不全，阶段一与阶段三需合并**，提前评估"降到 LLVM 16/18 + TypeCopilot"是否才是可行主干。这是全路线最大未验证假设。

### 阶段二：字段符号化与门控抽取实测（golden tests × 优化矩阵）
golden cases 在 `-O0`/`-Og`/`-O2 -g` 三档跑（3.3）。全程允许 numeric fallback，验证"失败不丢事实+置信度分档"落地。container_of 用人工标注三元组做 ground truth（6.3）。同时加入 branch-local backward slice，验证 `branch_fact/gate_seed_fact` 能定位目标分支、条件值和相关对象。

### 阶段三：类型恢复分支评估（TypeCopilot 作对照参考）
LLVM16 分支跑 TypeCopilot，对上述 golden cases 提供字段类型参考，量化主干（LLVM21+SVF 原生）的差距。据此决定 TypeCopilot 是否迁移、主干是否降版本、是否仅在低置信度场景选用。

> **验证纪律**：每步有实际输出（符号化字符串、卡住位置、SVF 中间结果、golden 通过/失败记录），不接受"应该可以"。

## 第十三部分：golden tests 量化验收标准（v3 新增，审阅必改项）

每个 golden case 的通过标准（缺一不算通过）：

| 验收项 | 标准 |
|---|---|
| 是否产生 fact | 目标访问必须产出对应 access_fact（哪怕低置信度） |
| symbolic path 匹配 | 与人工标注的符号化路径一致（case 1/2） |
| numeric_kind 正确 | `gep_offsets`/`byte_range`/`whole_object`/`unknown` 与样例行为一致 |
| confidence 符合预期 | 档位与来源匹配（如 case 1 应为 `dwarf`/`btf` 高档） |
| source_location 可回溯 | `spelling` 能定位回源码真实访问；`instruction_id` 在构建内唯一不撞 |
| 优化矩阵覆盖 | `-O0`/`-Og`/`-O2 -g` 三档各有记录，跨档用 `cross_opt_key` 对齐 |

case 1（普通 GEP）额外：字段名、字段类型、数值偏移一致。
case 2（container_of）额外：三元组 `(container_type, member_offset, recovered_field_chain)` 与人工标注一致。
case 3（alloc wrapper）额外：目标自定义分配函数被种子+传播正确标记，`semantic_op` 分类正确（同步 alloc vs `free_async`）。
case 4a（READ_ONCE/WRITE_ONCE）额外：宏栈可回溯，访问事实不因编译器屏障丢失。
case 4b（atomic/refcount）额外：真正原子指令被归入 `access_kind=atomic`，refcount 操作能映射为 retain/release。
case 5（queue_work/task_work）额外：异步入口 fact、summary `effects` 与 `effect_bindings` 都能落库。
case 6（branch/gate seed）额外：从目标分支能反向切到相关 load/GEP/call_arg，且 `gate_seed_fact` 关联到对象关系证据。

## 附录：v3 相对 v2 的修订清单

1. LLVM 锁精确 patch：主干 21.1.0，21.1.8 仅实验矩阵（2.1）。
2. 优化等级改 `-O0/-Og/-O2 -g` 对照矩阵，纠正"几乎都跑 -O0"错误表述（LLIF 在 -O2 -g 成功）（3.3）。

4. primitive_summary 升为 YAML schema，并加入 `effects/effect_bindings`（3.6）。
5. `op` 改名为 `semantic_op`，扩为 alloc/read/write/free/**free_async**/retain/release/escape，RCU 释放单独标 free_async（5.4/7）。
6. `access_kind` 新增维度（load/store/memcpy/memset/atomic/usercopy/call_arg），与 semantic_op 边界厘清、地址逃逸只归 `semantic_op=escape`（5.4）。

8. `object_id` 稳定性规则与 `object_scope` 约束（allocation_site/global/formal_param/synthetic），formal_param/synthetic 只作关系证据（5.6）。
9. `instruction_id` 改 `module_hash:function:bb_ordinal:inst_ordinal:ir_hash`，限定为 build-local stable；跨优化档使用 `cross_opt_key`（5.5）。

11. container_of 交叉验证明确：不与 uncontained 工程联跑，只复用测试思想+类型图概念，ground truth 由人工标注三元组提供（6.3）。
