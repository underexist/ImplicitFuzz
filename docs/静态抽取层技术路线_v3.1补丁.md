# 静态抽取层技术路线 —— v3.1 工程细则补丁

> 本文件是 `静态抽取层技术路线_v3.md` 的**增量补丁**，不重写 v3，只收口实现时的字段/契约歧义。
> 阅读方式：v3 定方向与规范骨架，v3.1 定字段级契约。二者冲突处以 v3.1 为准。
> 补丁范围：`svf_commit`、`semantic_op` 改名、summary `effects`、多 provenance、`numeric_kind`、`object_scope`、instruction_id 作用域、source_location 宏栈、golden tests 增补、TypeCopilot 措辞、BTF 字段布局参考、branch/gate facts、io_uring primitive 清单、动态验证接口、SQLite/Datalog 边界、syzkaller 映射、外部静态工具定位。

---

## P1. SVF commit pin（补 v3 §2 版本纪律）

v3 已锁 LLVM 21.1.0，但 v3 §2 写的"SVF 当前 HEAD"会移动，破坏可复现性。**约束**：
- 主干固定一个**已验证的 SVF commit**，不长期依赖 HEAD。
- `svf_commit`（完整 SHA）必须写入构建 manifest，与 `llvm_version`(21.1.0)、clang 版本、`opt_level`、ID 生成规则并列。
- 升级 SVF commit 需重跑全部 golden tests 后才能替换主干 pin。

## P2. `op` → `semantic_op` 改名并厘清（改 v3 §5.4）

v3 §5.4 把字段叫 `op` 并说它"描述对象生命周期"，但枚举含 `read/write`——这不是生命周期，是自相矛盾。**改正**：
- 字段更名为 **`semantic_op`**，定义为"抽象语义操作"（生命周期只是其中一类）：
  ```
  semantic_op = alloc | read | write | free | free_async | retain | release | escape
  ```
- 分组语义（供上层理解，不必进枚举）：
  - 生命周期类：`alloc` / `free` / `free_async` / `retain` / `release`
  - 数据访问类：`read` / `write`
  - 逃逸类：`escape`
- v3 中所有出现 `op=` 的地方（§5.4、§7、§11、§13）统一读作 `semantic_op=`。
- `free_async`（RCU 延迟/回调释放）仍不与 `free` 等价的约束不变。

## P3. `primitive_summary` 补 `effects` 数组（补 v3 §3.6）

v3 §3.6 的 schema 只有 `lifecycle`/`transfers_ownership`/`retains_reference`，能描述 alloc/free/refcount，但**描述不了 `list_add`/`queue_work`/`spin_lock`/callback 注册与触发**——而这些正是 io_uring 隐式依赖的主要载体。**补充**：新增 `effects` 数组，每个 primitive 可携带多个副作用：

```yaml
- name_pattern: "queue_work*"
  param_roles:
    - {index: 0, role: workqueue_handle}
    - {index: 1, role: work_item}
  return_role: none
  lifecycle: none
  is_async: true
  transfers_ownership: false
  retains_reference: true
  effects:                    # v3.1 新增：可组合的副作用
    - async_enqueue
    - callback_register
  confidence: high
```

`effects` 枚举（可扩展）：
```
lock_acquire | lock_release
| container_link | container_unlink      # list_add / list_del 类
| async_enqueue                          # queue_work / task_work 类
| callback_register | callback_invoke    # 回调注册/触发
| copy_from_user | copy_to_user
```
覆盖对象扩展为：分配/释放族、RCU、refcount、**list API（container_link/unlink）**、**workqueue/task_work（async_enqueue）**、**锁（lock_acquire/release）**、**回调注册/触发**、usercopy。§7 识别出的自定义包装函数并入本库时，一并标注其 `effects`。

**P3.1（追加）：`effects` 需绑定参数，否则"发生了注册"但"不知道注册的是谁"。** 补充 `effect_bindings`：
```yaml
  effect_bindings:
    - {effect: callback_register, callback_param: 1, context_param: 0}
    - {effect: async_enqueue, target_param: 1, context_param: 0}
```
每条 `effect_bindings` 把 `effects` 数组里的某个副作用，绑定到具体的参数角色（哪个参数是回调函数、哪个参数是承载异步执行的对象/上下文）。没有 `effect_bindings` 的 `effects` 视为不完整记录，第七部分/§8 识别 workqueue、task_work、回调注册时必须一并产出对应绑定，否则该 effect 不参与后续依赖推断，仅作弱提示保留。

## P4. `provenance` 改为多来源（改 v3 §5.1）

v3 §5.1 的 `provenance` 是单枚举，但一条 fact 可能同时来自多个来源（`svf + dwarf + summary`，或 `svf + container_of_heuristic + numeric_fallback`）。**改正**：
- `provenance: []`（数组，记录所有来源）。
- 新增 `primary_provenance`（单值，主导来源，用于置信度定档与快速过滤）。
- 枚举值扩展为：`svf` / `dwarf` / `dwarf_partial` / `btf` / `btf_partial` / `typecopilot` / `container_of_heuristic` / `numeric_fallback` / `summary`。
- 置信度模型（v3 §11）按 `primary_provenance` 定档，但 `provenance[]` 保留完整来源链供审计。

## P5. `access_path_numeric` 加 `numeric_kind`（改 v3 §5.4 的"始终正确填充"）

v3 §5.4 说 numeric "始终填充"，对 GEP 字段访问成立，但对 `call_arg`/`escape`/整对象 `memcpy/memset`/summary 合成对象**未必有字段偏移链**——"始终有 GEP 偏移"是把字段访问经验错误外推。**改正**：新增 `numeric_kind`，让"失败不丢事实"不被"必须有偏移链"绑死：
```
numeric_kind = gep_offsets   # 有完整 GEP 偏移序列（原 access_path_numeric 语义）
             | byte_range    # 只有字节范围（如部分 memcpy）
             | whole_object  # 整对象操作，无字段粒度（如整体 memset/escape）
             | unknown       # 无法给出数值刻画（如纯 call_arg 传递）
```
- `access_path_numeric` 内容按 `numeric_kind` 解释；`unknown` 时可为空，但 fact 仍产出（confidence 相应降档）。
- 契约：**"失败不丢事实"= 一定产出 fact + 一定有 `numeric_kind`**；不再要求"一定有 GEP 偏移"。

## P6. `object_id` 加 `object_scope` 并约束 formal_param（改 v3 §5.6，正确性关键）

v3 §5.6 的 `param_object(function, arg_index)` 表示"形式参数对象"，但同一函数会被不同调用点用不同实际对象调用——**若直接当身份等价，会把所有经过该 helper 的不同对象错误合并成同一身份，这是对象身份判定最危险的假阳性来源**。**改正并升为显式正确性约束**：

- 新增 `object_scope` 字段：
  ```
  object_scope = allocation_site | global | formal_param | synthetic
  ```
  与 v3 §5.6 的 `object_id` 分类对应（allocation_site_id / global_symbol / param_object / synthetic_stub_object）。
- **正确性契约（抽取层 ↔ 证据库之间的硬约束）**：
  - `object_scope = formal_param` 的对象 **不得**被证据库上层直接判为身份等价，**只能作为 relation evidence**。
  - 抽取层职责：如实标注"这只是形参线索"（打上 formal_param）。
  - 证据库上层职责：顺着 `call_fact` 的调用点，把 formal_param refine 成具体的 allocation_site / global 对象后，才可参与身份等价闭包。
  - `synthetic`（summary 兜底产生的合成对象）同理，不得直接判等价。
- 此约束若含糊，盲区分析会因跨调用点的错误对象合并而系统性出错，务必在 ingestion 与查询层同时校验。

## P7. `instruction_id` 限定作用域 + 跨优化档组合键（改 v3 §5.5）

v3 §5.5 的 `instruction_id`（`module_hash:function:bb_ordinal:inst_ordinal:ir_hash`）在**同一构建产物内**稳定，但**跨 `-O0/-Og/-O2 -g` 不保证同一源码访问有同一 ID**（优化会改变 bb/指令序号与 ir_hash）。v3 让它隐含承担了"跨优化档对比"的期待，这是错的。**改正**：
- 明确 `instruction_id` 为 **build-local stable**（仅在单一构建产物内唯一稳定，用于该产物内的回溯）。
- **跨优化档对比**（v3 §3.3 的优化矩阵、§13 的优化矩阵覆盖）改用组合键：
  ```
  cross_opt_key = source_location(expansion) + access_path_key + function + semantic_op
  ```
  用此组合键把不同优化档下"同一源码访问"对齐，而非依赖 instruction_id 相等。

**P7.1（追加）：`access_path_key` 需允许降级，不能直接用可能为空的 `access_path`。** numeric fallback 或 `numeric_kind=unknown` 时 symbolic path 可能为空，若组合键直接引用 `access_path` 会在这些场景断裂、导致优化矩阵对齐失败。改为三级降级取值：
```
access_path_key = symbolic_path || numeric_repr || source_snippet_hash
```
即优先用符号化路径，其次用数值表示（对应 `numeric_kind` 的偏移/字节范围表示），两者都不可得时退到"源码片段哈希"兜底，保证即使字段符号化完全失败，跨优化档的对齐依据依然存在。

## P8. `source_location` 扩为宏/内联栈（改 v3 §5.1）

v3 §5.1 的 `source_location` 只是 file:line，但 `container_of`/`list_for_each_entry`/`READ_ONCE`/`WRITE_ONCE` 大量是宏，纯 file:line 回溯会跳到头文件里的宏定义、定位不到真实访问点。**改正**：
```
source_location = {
  spelling:    file:line,     # 宏调用的书写位置（源码里实际写 container_of 的那行）
  expansion:   file:line,     # 宏展开后的位置
  inlined_at:  [file:line, ...]  # 内联调用栈（可空）
}
```
- P7 的 `cross_opt_key` 用 `expansion` 分量。
- golden test 的 "source_location 可回溯" 验收（v3 §13）以 `spelling` 能定位回源码真实访问行为准。

## P9. golden tests 增补现实样例（补 v3 §6、§13）

v3 的三个 case（普通 GEP / container_of / alloc wrapper）之外，新增轻量 case，覆盖 v3 新引入但当前无测试覆盖的枚举。**golden case 4 拆分为 4a/4b（v3.1 追加修订）**：`READ_ONCE/WRITE_ONCE` 与 `atomic_*` 在 LLVM IR 里的指令形态不同（前者多为编译器屏障+普通 load/store，后者是真正的原子指令），混在一个 case 里 ground truth 会含糊，拆开更清爽：

- **golden case 4a —— `READ_ONCE/WRITE_ONCE`**：验证这类编译器屏障宏对应的 `access_kind` 路径，确认单次访问的字段能被正确抽取。
- **golden case 4b —— `atomic_*` / `refcount_*`**：验证真正原子指令对应的 `access_kind = atomic` 路径。不要求首版立即实现，但 ground truth 与验收标准需与 4a 分开定义。
- **golden case 5 —— `queue_work/task_work` 异步入口**：验证 `entry_kind = workqueue|task_work|io_worker` 与 summary `effects = async_enqueue/callback_register`（含 P3.1 的 `effect_bindings`），确认异步执行路径被建模为入口、且不在 enqueue 处断裂。

新增 case 同样纳入 v3 §13 的量化验收表（是否产 fact / numeric_kind 正确 / confidence 符合 / source_location 可回溯 / 优化矩阵覆盖），ground truth 仍由人工标注。

## P10. TypeCopilot 措辞：oracle → differential reference（改 v3 §2.2、§11、§12 阶段三）

v3 把 TypeCopilot 称为"离线 oracle"。"oracle"在测试语境里过于接近"绝对正确的裁判"，但它本身是研究原型（锁 LLVM 16），不能僭越为 ground truth。**改正**：
- 统一改称 **"differential reference / 对照参考"**。
- 明确：**真正的 ground truth 只有人工标注的 golden cases**；TypeCopilot 只是用来度量"主干字段恢复与一个较强的第三方实现之间的差距"，其输出不等于正确答案，两者不一致时以人工标注为准。
- v3 §11 置信度表中 `typecopilot` 档位含义相应调整为"来自对照参考的恢复类型"，不因来自 TypeCopilot 就自动高于人工可核验的档位。

## P11. BTF 作为字段布局参考源（补 v3 §3.3.1、§5.1、§6.1）

补调研确认：BTF 记录类型、结构体/联合体成员名、成员类型与 bit offset，能通过 `pahole` 生成、通过 `bpftool btf dump` 导出。它不替代 SVF，但适合补 DWARF/GEP 符号化的盲区。**补充约束**：

- manifest 增加 `debug_info_kind`、`btf_available`、`pahole_version`、`vmlinux_btf_path`。
- `provenance[]` 增加 `btf`、`btf_partial`。
- `access_path_recovery` 增加 `btf`、`btf_partial`。
- BTF 只解释字段布局，不直接产生对象身份等价；若 BTF 与 DWARF/SVF 结果冲突，fact 保留、置信度降档，并记录冲突来源。

## P12. 新增 `branch_fact` / `gate_seed_fact`（补 v3 §5.8）

静态抽取层需要为后续"目标门控"和"隐式依赖调度"留下锚点，不能只输出对象访问事实。新增两类 fact：

- `branch_fact`：记录条件分支、switch、错误路径判断、状态位判断。核心字段：`branch_instruction_id`、`condition_value`、`source_location`、`control_deps`、`related_loads`、`slice_range`。
- `gate_seed_fact`：把与 fuzzing 目标相关的分支标成门控种子。核心字段：`target_symbol`、`gate_kind`、`predicate_summary`、`related_objects`、`related_access_facts`、`confidence`。

实现边界：第一版做 branch-local backward slice，从条件值沿 SVFG 反向追 value-flow，再辅以 LLVM Dependence Graph/轻量控制依赖记录。不要一开始做全程序 SDG，否则会把抽取层拖成另一个大型切片项目。

## P13. io_uring primitive summary 首轮清单（补 v3 §3.6、§14）

v3 只写"覆盖 list/workqueue/锁"还不够具体。io_uring 第一轮 summary 至少覆盖：

```
alloc/free/cache
RCU
percpu_ref/refcount
llist/list/xarray
task_work/workqueue/io-wq
mutex/spinlock
copy_from_user/copy_to_user
completion/cancel/timeout
```

其中 `task_work/workqueue/io-wq` 必须带 `async_enqueue`、`callback_register` 或 `callback_invoke`，并填写 P3.1 的 `effect_bindings`。`completion/cancel/timeout` 不一定是生命周期操作，但必须能落到 entry/gate 证据中，否则后续依赖图会漏掉大量完成路径和取消路径。

## P14. 动态验证接口：KCOV remote coverage 优先（补 v3 §9.4）

普通 KCOV 主要覆盖当前任务的 syscall 执行路径；io_uring 的 worker、task_work、io-wq、后台线程路径可能不在普通线程上下文里。补充验证策略：

- 普通同步路径：KCOV 足够作为覆盖验证入口。
- 异步/后台路径：优先评估 KCOV remote coverage。
- 若 remote coverage 在目标环境不可用或不稳定：把 kprobe/ftrace/eBPF 作为可选观测通道，用于确认异步入口、回调触发和门控分支是否被实际走到。

这部分不改变静态抽取层职责，只定义它需要输出哪些 ID 和 source location，方便动态侧回填证据。

## P15. SQLite 先行，Datalog 只作规模化备选（补 v3 §9.3）

第一版证据库仍采用 SQLite + 递归 CTE。Datalog/Souffle 不进入初始依赖，避免过早引入第二套规则运行时。触发迁移的条件：

- 递归规则数量增长到 SQL 难以维护；
- 跨 entry、跨异步入口的闭包查询性能不可接受；
- 需要大量固定点规则、半格合并或复杂数据流传播。

没有触发这些条件前，SQLite 是主线，Datalog 只保留接口可能性。

---

## P16. syzkaller 映射表，不直接生成最终规范（补 v3 §9.2）

静态抽取层输出需要保留 syzkaller 可消费的中间映射，但不要在本阶段承诺生成最终 `.txt` 描述。映射关系：

- `semantic_op=alloc/retain/release/free` → resource 生命周期候选；
- `copy_from_user/copy_to_user`、`call_arg`、`field_type` → syscall 参数/结构字段候选；
- `gate_seed_fact.predicate_summary` 与 `related_objects` → 隐式门控参数候选；
- `entry_fact` 的 syscall/file_op/ioctl/uring_cmd → syzkaller syscall description 入口。

后续阶段再把这些证据合成为 syzkaller resource、结构字段和约束。

---

## P17. 外部静态工具只做辅助交叉检查（补 v3 §10）

Smatch、Sparse、Coccinelle、CodeQL 不进入主链。它们的合理用途是：

- 辅助检查 `primitive_summary.yaml` 是否漏掉常见 API；
- 为 golden cases 做交叉 sanity check；
- 人工标注时快速定位 list/refcount/usercopy/locking 模式。

这些工具不能替代 SVF 的跨函数值流、points-to 证据，也不能把它们的报告直接当作对象身份证据。
